number means, so it is stated on every output.

## `maude`: real data

### Provenance

US FDA Manufacturer and User Facility Device Experience database, retrieved
through the openFDA `device/event` endpoint. openFDA data is dedicated to the
public domain under CC0 1.0: redistribution and commercial use are permitted and
no attribution is legally required. I attribute anyway.

`src/fetch_maude.py` writes `data/maude_provenance.json` recording the endpoint,
the exact query, the years covered, the record count and the retrieval timestamp.
That file is the citation for any figure produced from this corpus.

GMDN device terminology requires separate licensing and is **not** requested or
stored.

### Inclusion

A raw report enters the corpus only if it carries all of: a receipt date, at
least one coded product problem, at least one recorded remedial action, and a
narrative of at least 40 characters assembled from `mdr_text` entries of type
*Description of Event or Problem* or *Additional Manufacturer Narrative*.
Everything else is dropped, not imputed.

### Fields taken directly from MAUDE

| Field | openFDA path |
|---|---|
| `report_number` | `report_number` |
| `date_received` | `date_received` |
| `event_type` | `event_type` |
| `product_problem` | `product_problems[0]` |
| `remedial_action` | `remedial_action[0]` |
| `manufacturer` | `manufacturer_name`, else `device[0].manufacturer_d_name` |
| `product_code` | `device[0].device_report_product_code` |
| `brand_name`, `device_class`, `specialty` | `device[0]` and its `openfda` block |
| `narrative` | concatenated `mdr_text[].text` |

### Fields I derive, and how

These are **not** in MAUDE. `derived_fields` on every record lists them.

**`action_class`**: my grouping of MAUDE's remedial-action vocabulary into four
interpretable classes. The grouping is a modelling choice, not an FDA
classification; raw `remedial_action` is retained so it can be regrouped.

| Class | MAUDE values |
|---|---|
| Engineering / design | Recall, Repair, Replace, Modification/Adjustment |
| Communication | Relabeling, Notification |
| Surveillance | Inspection, Patient Monitoring |
| Other | Other, None |

**`recurred_within_365d`**: the outcome the project is about, and the reason it
can be studied on public data at all. For each report, `1` if another report
exists with the same *(product code, manufacturer, primary product problem)* and
a receipt date in the interval `(D, D+365]`, where `D` is this report's receipt
date.

**`group_size`, `n_prior_in_group`**: the number of reports sharing the group
key, and how many precede this one. Carried because they confound the outcome:
a device that is reported more is mechanically more likely to be reported again,
whatever action was taken.

**`observable`**: `1` when the report has a full 365-day follow-up window inside
the corpus, i.e. `date_received <= max(date_received) - 365`. Reports near the end
of the window have had less time in which to recur, so including them biases the
estimate downward and does so worst for the most recent reports.
`store.load()` drops non-observable rows by default.

### Known limitations of this corpus

These are properties of MAUDE, not of the pipeline, and they bound what can be
claimed.

1. **Passive, voluntary surveillance.** Reporting rates vary by manufacturer,
   device, year and regulatory attention. FDA states MAUDE cannot be used to
   evaluate rates of adverse events or to compare devices.
2. **No denominator.** Units sold or in service are unknown, so recurrence here
   is *reports following reports*, not risk per device.
3. **Duplicates and supplements.** The same event can generate multiple reports.
   No deduplication beyond `report_number` is performed.
4. **`remedial_action` is manufacturer-reported** and describes what was recorded,
   not necessarily what was done or how well.
5. **Association, not causation.** Action type is chosen partly in response to
   severity, device class and manufacturer capability. `experiments.py --adjusted`
   controls for reporting volume only; residual confounding remains.
6. **Group key is a modelling choice.** A different key changes the recurrence
   estimate. Its sensitivity is not yet quantified.

Any claim from this corpus should be phrased as *reports of the same problem for
the same device and manufacturer recurred within a year*, not as *the problem
recurred*.

## `synthetic`: generated, for learning

Generated by `src/synth.py`. Identifiers are prefixed `DEV-SYN-` and
`CAPA-SYN-` so no record can be mistaken for a real quality event.

Three structures are planted deliberately, and all three are documented rather
than hidden:

1. Cause category is inferable from narrative vocabulary.
2. Recurrence depends on the action type.
3. 14% of non-human-error events are recorded as *Human Error* regardless of
   narrative, modelling the category a quality system defaults to under close-out
   pressure. This sets the classifier ceiling.

Because the central relationship is planted, this corpus can demonstrate that a
method **recovers** a relationship. It cannot provide evidence that the
relationship holds anywhere. Do not report a number from it.

## The offline fixture

`src/fixture.py` generates MAUDE-*shaped* records for testing the transformer and
the recurrence derivation without network access. Report numbers are prefixed
`FIXTURE-` and every record carries `_fixture: true`. `src/build_corpus.py` refuses to
build an analysis corpus from it unless `--allow-fixture` is passed.

The fixture contains no relationship between action and recurrence. A correctly
built pipeline therefore produces a recurrence model that **fails its gate** on
fixture input. That is the intended behaviour and a useful check that the gate is
not rigged.
